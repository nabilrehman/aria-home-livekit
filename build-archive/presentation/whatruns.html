What Runs Where

"LiveKit is a cloud platform, so it all runs in LiveKit Cloud" — the sentence that makes the architecture diagram impossible to read. Here's what's actually true.

You already ran the whole thing today. It just ran on your laptop, and nobody told you that was the cloud box.

01

There are two systems, not one

The confusion comes from a reasonable assumption: LiveKit is a cloud product, so surely LiveKit runs everything. It doesn't, and the reason it doesn't is the most important thing on this page.

A voice agent is really two separate systems that meet in a room, and they are owned by different people.

Everything your agent did today — knowing order 44721 was a shipped thermostat, refusing to refund the cancelled one, calling your ticketing boundary — is on the right. That is your business, and LiveKit deliberately doesn't run it, because if they did, every company's agent would be identical.

The whole primer in one line

LiveKit runs the room and the models. You run the agent. "Where does LiveKit run" is a fixed answer; "where does the agent run" is the actual design decision — and today the answer was "your laptop."

Which means

The box labelled "AWS" in the reference diagram is not LiveKit. It's the second system — yours — and it's showing one of three places you could have put it.

02

The agent is a container that phones home

Here's the mechanical fact that makes the three options possible. Your agent doesn't wait to be contacted. It reaches out to LiveKit and says "I'm here, dispatch me work." From the docs, verbatim: "LiveKit Agents run as containers, so you can deploy them to LiveKit Cloud or to any Kubernetes cluster."

You saw this exact line in your own logs today:

registered worker {"agent_name": "anycompany-agent",
                  "url": "wss://personal-mv5pzdc8.livekit.cloud",
                  "region": "US Central A"}

Read that carefully. Your laptop made an outbound connection to LiveKit and registered. Nothing connected to your laptop — no port was opened, no address was exposed. It dialled out, said its name, and waited.

This is why it can run anywhere. A thing that only makes outbound connections doesn't care whether it's on your desk, in LiveKit's data center, or in your own cloud — from LiveKit's side it looks identical. It's a worker that showed up for a shift.

Why this matters for a security review

"Where does your code run, and what do we have to expose?" is a question every enterprise asks. The answer is strong: the agent makes only outbound connections, so there's nothing inbound to firewall. You can run it deep inside a private network and it still works.

So the real question is just

Where do you want that container to run? There are exactly three answers, and they're a progression.

03

The three places, and you've already used one

Notice the progression. Option 1 is where you start. Option 2 is the easy production path — LiveKit runs your container for you, still on their infrastructure. Option 3 is when a customer says "our data can't leave our Google Cloud" or "we already run everything on GKE, put it there" — and then the agent lives in their cloud, next to their systems.

Say it like this

"Your agent is a container. In development it runs on my laptop. For production you've got two choices — let LiveKit host it with one command, or run it in your own cloud next to your data. Same code either way. The reference diagram shows it running in your cloud, which is what you'd want if data residency matters or you're already on Kubernetes."

04

What actually happened on your laptop

Let's make option 1 concrete, because you lived it and it demystifies the other two. When you ran lk agent dev, your MacBook became the entire right-hand box of the diagram. Here's the whole picture, honestly labelled:

The order data lived in a Python file on your disk. The tools ran in your local process. The agent connected out to LiveKit over your home internet. It all worked — you took a real phone call through it.

And every weakness of a laptop-as-production showed up: a 1.66-second cold start when a call arrived and no process was warm, and the whole thing would vanish the moment you closed the lid. Those aren't bugs. They're the reason options 2 and 3 exist.

So porting to GCP is not a rewrite

It's picking up that right-hand box and setting it down somewhere that never sleeps. The code doesn't change. The address it phones home to doesn't change. Only the floor under it changes.

05

Porting the box to Google Cloud

Take each thing that was on your laptop and ask "what's the always-on version of this on GCP?" That's the entire port. Nothing is invented; each piece just moves from your disk to a managed service.

On your laptopOn GCPWhy
the agent process (lk agent dev)GKEa voice call is long-lived and sticky — it must stay on one machine for its whole life, and you scale by adding machines. That's Kubernetes' shape, not a request-response one.
the Next.js web app + token serverCloud Runstateless, request-shaped, bursty. Scales to zero when idle. The opposite of the agent.
store.py (fake orders)Firestorea real database that survives restarts and many readers. Your dict-in-memory becomes documents.
model API keys in .env.localSecret Managersecrets don't belong in files on disk. Mounted at runtime, rotated, audited.
"no static keys" (you had keys in a file)Workload Identitythe pod assumes a Google identity — no key material anywhere. This is the "IAM instance role · no static keys" note on the diagram.
logs scrolling in your terminalCloud Logging / Traceper-turn latency as trace spans, searchable, retained.
serving the browser from localhostCloud CDN + Load Balancingthe edge for web customers. The "CloudFront" box.

The one row worth arguing about is the first. The instinct is to put the agent on Cloud Run too, since it's the easy default — and it's the wrong call. Cloud Run is built for requests that arrive, get handled, and finish; it caps a request at sixty minutes and it wants to scale to zero. A voice session is the opposite: it hangs on for the length of the call, holds state, and can't be moved mid-conversation. That's exactly what GKE is for. GKE for the agent, Cloud Run for the web app is the split that shows you understand the workload rather than reaching for the default.

Say it like this

"Porting to GCP isn't a rewrite — the agent container is identical. You're just deciding where it runs. I'd put the agent on GKE, because voice sessions are long-lived and sticky and Cloud Run is built for short requests. The web app and token server go on Cloud Run, where scale-to-zero actually helps. Firestore for the data, Workload Identity so there are no static keys, and I'd pick the region to sit next to LiveKit's inference so I'm not adding a hop per turn."

06

The GCP pieces that make the agent smarter

Everything so far just moved the laptop's box to always-on infrastructure. But once the agent lives inside Google Cloud, it can reach for things the laptop never could — and this is where a GCP-native architecture earns its place rather than just matching AWS.

Vertex AI — Google's models, in the customer's own cloud

Your agent called LiveKit's hosted models today. A GCP customer might want the models to run in their Google Cloud instead — for data residency, for an existing Vertex commitment, or for consolidated billing. Vertex AI is Google's managed home for models: Gemini for the LLM, Chirp for speech-to-text, and Google's text-to-speech voices. The agent can point at Vertex instead of LiveKit Inference, and now the customer's audio and reasoning never leave their own project.

The honest caveat, and you should say it: the stack LiveKit hosts is there because each piece is a latency leader. Swapping to Vertex for procurement reasons can cost real milliseconds, and that's a measurement, not an assertion — offer to benchmark both against their traffic rather than promising either way.

A RAG engine — so the agent knows things it wasn't told

Here's a gap you felt today. Your agent knew about orders because you handed it order data. But ask it "what's your return policy?" or "is the thermostat compatible with my old boiler?" and it has nothing — that knowledge lives in PDFs, help articles, and manuals, not in your database.

RAG — retrieval-augmented generation — closes that gap. You take all that documentation, turn it into a searchable index, and give the agent a tool: when a customer asks a knowledge question, the agent searches the index, pulls the three most relevant passages, and answers from them instead of guessing. On GCP this is Vertex AI Search (formerly the RAG/Search engine): point it at a bucket of documents and it handles the indexing and retrieval.

Backend APIs — reaching the systems that already run the business

Your fake store.py stood in for something real, and in a live deployment the agent talks to the customer's actual systems: an order service, a CRM like Salesforce, a billing platform, an inventory API. On GCP those calls go out through the same tool mechanism you already built — a @function_tool that makes an HTTP request — reaching services that might be other Cloud Run services, an internal API behind a load balancer, or a third party across the internet. Nothing about that is new to you; it's your order-lookup tool pointed at a real endpoint instead of a Python dict.

The pattern under all three

Vertex, RAG, and backend APIs are the same move you already know: the agent doesn't hold knowledge, it fetches it — from a model, from a document index, or from a business system. Your whole day was practice for this. The tools just point somewhere real.

—

Five things to carry

  1. There are two systems. LiveKit runs the room and models; you run the agent. "Where does LiveKit run" is fixed; "where does the agent run" is the design decision.
  2. The agent is a container that phones home. Only outbound connections — which is why it can run anywhere and why there's nothing to expose.
  3. Three homes: laptop, LiveKit Cloud, your cloud. Same code. You used the first today; the diagram shows the third.
  4. Porting to GCP is a move, not a rewrite. Each laptop piece becomes an always-on GCP service: agent→GKE, web→Cloud Run, data→Firestore, keys→Workload Identity.
  5. Inside GCP the agent gets smarter. Vertex for models in the customer's cloud, Vertex AI Search for RAG over their docs, function tools for their real backends — all the same "fetch, don't guess" pattern you already built.
