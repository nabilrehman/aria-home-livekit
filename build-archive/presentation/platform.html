Interview prep · Part four

What LiveKit Ships

A tour of the platform surface — the media server, the Agents framework, telephony, egress and ingress, deployment, and the plan lines that decide what a customer can actually have. Written from the docs, with the weak spots left in.

Companion to From Sound to Conversation, AnyCompany Voice Agent Playbook, and Inside the Room. Those cover the physics of a voice agent, the whiteboard script, and what a room and an SFU really are. This one assumes all three and does not repeat them.
Verified against docs.livekit.io and livekit.com, August 2026. Sources listed at the end.

01

One server, one framework, four services

When a customer says "we're evaluating LiveKit," they might mean five different things, and your first job in a technical conversation is to find out which. The word covers an open-source project, a managed cloud, a Python library, a telephony product, and a recording service. They are genuinely separable — you can adopt some and not others — and knowing where the seams are is most of what makes you useful in the room.

Start at the bottom. LiveKit server is an open-source WebRTC Selective Forwarding Unit written in Go, Apache 2.0 licensed. It does signalling, NAT traversal, RTP routing, adaptive degradation, and quality-of-service. You already know what an SFU is; the thing to notice here is that this single binary is the same code whether it's running on your laptop, in your EKS cluster, or inside LiveKit Cloud. The docs are explicit about this: Cloud "runs the same open-source LiveKit server available on GitHub and supports the same APIs and SDKs," and "the connection endpoint is the primary difference." That claim is load-bearing for a pre-sales conversation, because it is the answer to what happens if we want out.

Above the server sits the Agents framework — a Python SDK and a Node.js SDK that let an ordinary program join a room as a first-class participant, receive the audio, run it through models, and publish speech back. It is also open source. It is not a hosted product on its own; it's a library you run somewhere, and "somewhere" can be LiveKit Cloud or your own Kubernetes.

Beside those two are the integration services, which exist because not everything speaks WebRTC. Telephony (the SIP service) bridges the phone network into a room. Egress pulls media out of a room and turns it into files or livestreams. Ingress pushes media from RTMP, WHIP, SRT, or a plain HTTP file into a room. Each of these is a separate service you deploy yourself when self-hosting, and each is simply there, preconfigured, on Cloud.

And then the SDKs: client SDKs for the platforms your users are on, and server SDKs for your backend to mint tokens and call management APIs. Every one of these participants — a browser, a phone caller, an agent, an egress recorder, an ingress transcoder — shows up in the room the same way, as a participant with tracks. That uniformity is the platform's central design decision, and it is why the pieces compose as cleanly as they do.

Keep this one

LiveKit is an open-source SFU plus an open-source agent framework, and LiveKit Cloud is a managed platform built around them that adds hosting, inference, telephony numbers, and observability. The client and agent code is portable in both directions. That portability is the honest answer to lock-in, and it is unusual enough in this market to be worth saying plainly.

02

What Cloud is actually selling

Most managed offerings are "the same software, but we page the on-call." LiveKit Cloud is not that, and the difference is architectural rather than operational. It is worth understanding properly, because it is the single most defensible technical claim the company has.

A conventional media server is single-home: a session lives on exactly one machine. You can run a hundred machines in a dozen data centres, but everyone in a given call must connect to the same one. That has three consequences the LiveKit engineering blog states directly. It's a single point of failure, since all the session state is in one process's memory. It caps scale at whatever one box can forward — their worked example puts a fifty-person video call at roughly 1.23 Gbps of outbound bandwidth, near the sustainable limit of most network links. And it puts distant participants a long way from the server, which matters more than raw latency suggests: WebRTC repairs lost packets by having the receiver send a NACK and the sender retransmit, so a far-away server makes every repair slower.

Cloud is multi-home. A session stops being a machine and becomes a logical object that can span servers and data centres. Each participant connects to the nearest edge; the edges relay tracks to each other over a private overlay network — encrypted, multi-cloud, every instance addressable by every other — using a custom FlatBuffers-based relay protocol rather than WebRTC, because ICE and SDP buy nothing between two servers you already control. Participant presence is synchronised over a per-session pub/sub topic rather than a database, on the reasoning that the state is transient, there's a natural write authority (the server the participant is attached to), and eventual consistency is fine.

Two consequences are worth memorising. First, the mesh reshapes itself per track: for a livestream with one publisher and twenty thousand viewers the relays organise into layers, and for a big conference the same servers form a full mesh. Second, live migrations — when a server needs to go away, the client does a WebRTC ICE restart pointed at a different server, and the new server reconstructs the participant's expected state, including existing subscriptions. A failure that would normally cost a five-second teardown-and-rejoin becomes under a second, and it works proactively too, so they can drain a sick machine before anyone notices.

Regions, residency, and the catch

Cloud publishes ten region groups for realtime traffic — us, eu, asia, india, me, africa, aus, il, sa, uk — with a note that the list changes and was last updated in May 2026. Some have more than one location and therefore in-region redundancy; the single-location ones (Africa, Australia, Israel, South America, UK) do not, and the docs say plainly they "can't offer the same availability guarantees."

Region pinning keeps a project's traffic inside a chosen group for data-residency reasons, and it is the one feature where the honest answer is a trade. The docs state it directly: "when you enable region pinning, you turn off automatic failover to the nearest region in the case of an outage." It's also gated to the Scale plan and has to be switched on by LiveKit support. And it works by embedding region selection in the signalling protocol, which means it only works with the realtime SDKs — SIP has to use region-specific endpoints instead, and SIP's region codes are not the same codes. sa means South America for realtime and Saudi Arabia for telephony. That's the kind of detail that makes you look like you've read the manual.

Say this honestly

Residency and resilience pull against each other here. If a customer needs EU-only processing, they get EU-only processing and they give up automatic cross-region failover — they're relying on France and Germany covering for each other instead of the whole network. That's a fine trade for most regulated buyers, but say it before they find out.

03

Agent servers, dispatch, and jobs

The Agents framework has a three-level structure that trips people up on first contact, so it's worth getting the vocabulary exactly right — the docs recently renamed some of it, and older material and blog posts still say "worker" where the docs now say "agent server."

Your process, when it starts, registers itself with LiveKit server as an agent server and then waits. That registration is an outbound WebSocket, which has a pleasant operational consequence worth mentioning to any security team: agent servers "do not need to expose any inbound hosts or ports to the public internet." Nothing dials into your fleet.

When work arrives, LiveKit routes a request to an available agent server, which accepts it and forks a job — a separate OS process that joins the room and runs your entrypoint function. One process per session. If a job segfaults or runs out of memory, it takes down that conversation and nothing else; if the parent agent server dies, all its children die with it. That isolation costs memory but it is the right default for something that will be running arbitrary model code on a live call.

The middle step, dispatch, is where the design decisions live. There are four ways an agent gets attached to a room:

  • Explicit, via the AgentDispatchService API from your backend. This is what the docs recommend for most applications, and it's the only path that gives you full control over timing plus a metadata string (up to 512 KiB, JSON by convention) handed to the job — the customer ID, the account context, the reason for the call.
  • Explicit, via the access token. You embed a RoomConfiguration with agent dispatch entries in the participant's JWT. Note the trap: this only fires when the room is first created. If the room already exists, the token's dispatch config is silently ignored.
  • Explicit, via a SIP dispatch rule, for inbound phone calls. Same mechanism, configured on the telephony side.
  • Automatic, which happens when you don't set an agent name — every new room gets an agent. The docs carry a caution against it: it fires regardless of whether an agent is wanted and it can't pass metadata. Fine for a prototype, wrong for a product.

Two numbers are worth carrying. Dispatch is optimised for "hundreds of thousands of new connections per second with a max dispatch time under 150 ms." And if an agent vanishes from a live room — crash, OOM, node loss — LiveKit server notices "within approximately 15 seconds and automatically dispatches a new agent to the room." Fifteen seconds of silence is a long time on a phone call, so that's a recovery story, not a resilience story, and worth framing as such.

Two more knobs matter for capacity conversations. Prewarming keeps a pool of idle processes with your models already loaded, sized by CPU count by default, so a new call doesn't wait on a cold Python import. And load is a function you can override: the default reports average CPU over a five-second window and the server stops accepting jobs above 0.7. On LiveKit Cloud deployments you cannot change those two parameters — they're for self-hosted fleets only. LiveKit's own sizing guidance for self-hosters is four cores and 8 GB per agent server, handling ten to twenty-five concurrent jobs depending on what's in the pipeline.

04

Choosing the brain

You already know the two shapes — a cascade of speech-to-text, LLM, and text-to-speech, versus a single speech-to-speech model. What's worth adding here is that LiveKit supports a third, and has an opinion about which to pick.

The opinion is stated flatly: "For most production agents, an STT-LLM-TTS pipeline is the right default." That is a slightly unfashionable position and a useful one to be able to defend, because the reasons are all operational rather than aesthetic. Text at every boundary means you can log it, audit it, replay it, and swap any one stage without touching the others. Tool calling on text LLMs is more mature and more predictable than audio-native tool calling. Interim transcripts exist, so live captions work. And say() reads an exact script, which matters enormously the moment a compliance team wants a disclosure worded a particular way.

The third shape is half-cascade: a realtime model for understanding the input, and a separate TTS for the output. You keep the model's ability to hear tone and hesitation, and you keep script-exact output. The cost is that you're now operating two models instead of one or three, and not every realtime provider supports a text-only response mode.

LiveKit Inference

Whichever shape you pick, you have to get to a model. The default path used to be a plugin per provider plus an API key per provider, which is fine until you're managing a dozen keys and a dozen billing relationships. LiveKit Inference is Cloud's answer: a single interface to LLM, STT, and TTS models from OpenAI, Google, Deepgram, AssemblyAI, Cartesia, ElevenLabs, Speechmatics, xAI and others, with no provider keys and no plugins, billed through your LiveKit account.

The claim that matters to a security reviewer is zero data retention: "your prompts, audio, and model outputs pass through only to generate a response. Neither LiveKit nor the underlying model providers log, store, or train on your data." Every model, every plan, no configuration. Note carefully what that doesn't cover — it is separate from agent observability, which you opt into and which does retain session data in Cloud, and separate from custom voices, which store the sample you upload.

The plugin path still exists and is the escape hatch: forty-plus TTS providers, twenty-plus STT, twenty-plus LLM including Anthropic, Bedrock, Ollama for on-prem, and OpenAI-compatible endpoints for anything else. So "we already have an ElevenLabs contract" or "our LLM must run in our VPC" are both answerable without leaving the framework.

Worth having ready

Model rosters churn fast — the inference docs carry explicit deprecation and retirement dates per model, some only weeks out. Don't memorise model names for an interview. Memorise the shape: one interface, many providers, ZDR by default, plugins as the escape hatch, and a published retirement policy you should point a customer at rather than a list you'll get wrong.

05

Structuring a conversation

A customer-service agent is never one prompt. It's an intent router, then a lookup, then some structured data collection, then an action, and possibly a handoff to a person. The framework gives you four constructs for that, and the interesting thing is that the docs are unusually forceful about not reaching for the fancy ones early.

AgentSession is the orchestrator — it collects input, runs the pipeline, calls the model, publishes the output, and emits events (agent_state_changed, user_input_transcribed, conversation_item_added, close) that your frontend and your logging both hang off. Inside it sits at least one Agent: instructions, tools, model choices. Those two you always have.

The other three are optional and they differ in who holds control of the session. Tools are functions the model can call; they don't take control, they just return a value. Tasks are short-lived units that take temporary control, run their own turn loop to collect and validate something, and return a typed result — this is the supervisor pattern, and it's how you get a reliable credit-card capture without polluting the main prompt. Task groups sequence tasks and, critically, let a user go back and correct an earlier step. Handoffs transfer control permanently to a different agent, with context passed explicitly or deliberately reset.

The named limitations are worth quoting, because "when should we split this into multiple agents?" is exactly the question a customer will ask you: instruction bloat, where the prompt gets big enough that the model degrades at its main job; conflicting tool access between phases; multi-turn data collection that needs its own validation loop; and backtracking. Absent one of those, one agent with a changing tool set is the recommendation.

There is also a set of prebuilt tasks that will save a customer real weeks: GetNameTask, GetEmailTask, GetAddressTask, GetDOBTask, GetPhoneNumberTask, GetCreditCardTask, GetDtmfTask, and WarmTransferTask. Each handles the ugly part — spoken digits, noisy transcription, international formats, validation and re-ask. Similarly there are prebuilt tools including EndCallTool and send_dtmf_events. If you draw a customer-service flow on a whiteboard, being able to say "these five boxes ship in the box" is a strong moment.

For reaching outside, tools can be plain functions, they can be forwarded to the frontend over RPC so the browser fulfils them, or they can come from an MCP server over streamable HTTP, SSE, or a local stdio process, with header-based auth and tool filtering. One caveat: the MCP page is marked available in Python and not Node.js. Parity between the two SDKs is generally good but not total, and it's better to check than to promise.

06

Telephony

For a customer-service buyer this is usually the deciding section, and it's the one with the most moving parts. Note before you go looking: the telephony docs moved from /sip/ to /telephony/. Older links redirect or dead-end, and some pages still contain stale /sip/ cross-references. If you cite a URL in the interview, cite the new one.

Telephony adds exactly two concepts to the three you already know. A trunk is the configured relationship with a SIP provider — an inbound trunk accepts calls and can be locked down by source IP or dialled number, an outbound trunk places them and can be stored once or passed inline per call. A dispatch rule is attached to a trunk and decides which room an inbound caller lands in. Everything else is the primitives you already have: the caller becomes a SIP participant, which is an ordinary participant with some extra attributes, managed by the ordinary participant APIs.

There are three rule types and the choice has privacy consequences. An individual rule gives every caller their own room, named after their phone number plus a random suffix. A direct rule puts everyone in one named room. A callee rule names the room after the number that was dialled, optionally randomised per caller. The docs warn about both ends of this: shared rooms mean unrelated callers can hear each other, and individual rules put a phone number into a room name, which propagates into logs and traces throughout LiveKit and is not removed by PII redaction. For a regulated customer the right answer is to route each call to a predetermined room with an opaque ID.

LiveKit Phone Numbers

You can bring your own carrier — the docs list Twilio, Telnyx, Plivo, Wavix, Sinch, didlogic and Exotel as tested, with a note that the service is designed to work with all SIP providers but compatibility testing is limited to those. Or you can buy the number from LiveKit. LiveKit Phone Numbers sells local and toll-free US numbers directly, with no trunk configuration at all: buy a number, attach a dispatch rule, done. Every Cloud plan includes one free US local number.

Two real limits

LiveKit Phone Numbers is US-only and inbound-only — outbound is described as "coming soon." A customer wanting outbound campaigns, or numbers in the UK or India, needs a third-party trunk. That doesn't block anything, but it changes the setup story from "click a button" to "configure a carrier," and you should say so before they discover it in a POC.

Transfers, and the rest of the feature list

Escalation to a human is the feature customer-service buyers care about most, and there are two mechanisms with genuinely different semantics. A cold transfer (call forwarding) issues a SIP REFER; the carrier re-points the call at another number or SIP endpoint and the caller's LiveKit session closes. It's simple and it's final — no context travels, and if the destination doesn't answer, you've already let go. A warm transfer keeps the LiveKit session alive: the agent dials the human into the conversation, briefs them with a summary, can put the caller on hold music meanwhile, and can come back to the caller if the transfer fails. There's a WarmTransferTask that implements the whole pattern.

The rest of the telephony surface, briefly: DTMF both ways (RFC 2833 / 4733), so your agent can navigate someone else's IVR and callers can press keys into yours. Answering machine detection, which classifies an outbound answer as person, voicemail, IVR, or unavailable — essential for outbound campaigns and, notably, a thing you'd otherwise buy separately. HD voice via wideband codecs. Secure trunking with TLS signalling and SRTP media. Region-based SIP endpoints and a destination_country parameter for outbound, both for regulatory isolation. And Krisp noise cancellation applied at the trunk for inbound and outbound calls — a Cloud-only capability, and a real one, because phone audio is 8 kHz and full of car noise, and cleaning it before STT improves transcription, turn detection, and recordings all at once.

Finally, the honest gaps. The docs publish an explicit support matrix, and four rows say "not supported": SIP REGISTER, SIPREC, and video over SIP. A customer whose contact-centre recording compliance runs on SIPREC will need a different approach — LiveKit's own egress, most likely — and it's much better for you to raise that than for their telecoms architect to.

07

Egress and Ingress

These two are the least-known parts of the platform and among the most immediately useful in a customer-service deal, because "record every call" is table stakes and "record every call" is not something the agent framework does for you.

Egress takes media out of a room. It comes in five shapes, and the shapes matter because they have very different costs. RoomComposite renders the room through a headless Chrome using a web layout you can customise, then encodes with GStreamer — the expensive, flexible option, and it stops automatically when the room ends. Web egress is the same machinery pointed at any web page, not necessarily a LiveKit room. Participant egress captures one participant's audio and video together. TrackComposite syncs one audio and one video track. And Track egress exports a single track with no transcoding at all — which is how you stream audio to a third-party captioning service over WebSocket. Auto egress isn't a sixth type but a switch on CreateRoom that starts recording the moment a room exists.

Outputs go to MP4, OGG, WebM, HLS segments, or out over RTMP to YouTube, Twitch, or anywhere else. For a voice-only deployment, the useful detail is that audio-only egress is billed at a lower rate, but only if you use an egress type that supports it: set audio_only=true on RoomComposite and do not set a layout or custom base URL, because either of those forces the job through the video pipeline. That's a genuine cost-saving tip and precisely the kind of thing a solutions engineer earns their keep with.

Ingress is the mirror. It exposes public RTMP and WHIP endpoints, or pulls from an HTTP or SRT server, transcodes through GStreamer, and publishes into a room as an ordinary participant — with simulcast layers you configure at creation time. For voice agents it's a niche capability, but it's the reason "can your agent listen to our existing broadcast feed?" has a yes.

Limits to state up front

Egress has hard time caps: three hours for file output, twelve for HLS segments, streaming, and raw track export. Hitting one ends the egress with LIMIT_REACHED — the data already captured is still delivered, and you get an egress_ended webhook. Concurrency is also low on the free plan: two ingress and two egress requests. Anyone planning always-on recording of a call centre is on a paid plan by definition.

Data, state, and the client surface

Voice is not the only thing moving through a room, and for a customer-service agent the non-voice channels are what make the experience feel finished — showing the transcript live, pushing an order summary into the page, letting the agent trigger a UI change, handing the user a PDF.

There are five data mechanisms and they differ along one axis: whether delivery is guaranteed or whether staying realtime matters more.

You want to…UseDelivery

RPC deserves a moment because it changes what an agent can do. A frontend registers named methods before joining; the agent calls them and waits for a return value. Combined with tool forwarding, this means an LLM tool call can be fulfilled by the browser — read something only the client knows, or manipulate the UI directly. "The agent highlights the right field on the form while it talks you through it" is an RPC, and it demos extremely well.

Participant attributes are a per-participant string key-value store, synchronised by the server and delivered automatically to anyone who joins later; initial values can be baked into the access token so they're present the instant the participant connects. Room metadata is the room-wide equivalent. Both have limits worth knowing: metadata caps at 512 KiB, attributes at 64 KiB across all keys, and neither is built for high-frequency updates — the docs say more than once every few seconds is the wrong tool, and to reach for data packets instead.

09

Who is allowed to do what

The auth model is small enough to hold in your head, which is a virtue. Every connection carries an access token: a JWT, signed with your API secret, minted by your backend. LiveKit never sees your users' credentials and has no notion of your user accounts. The token says who this participant is, which room they may join, and what they may do there.

The payload is a standard JWT — exp, iss (your API key), sub (participant identity), nbf — plus LiveKit's own claims. The video grant carries the room permissions: roomJoin, roomCreate, roomAdmin, roomRecord, ingressAdmin, and the per-participant capabilities canPublish, canSubscribe, canPublishData, canPublishSources (restrict to camera, or microphone, or screen share), canUpdateOwnMetadata, and hidden. A separate sip grant gates telephony: admin to manage trunks and dispatch rules, call to place outbound calls. And the token can carry a RoomConfiguration, which is how token-based agent dispatch works.

Two behaviours you should know because they come up in security review. Tokens are proactively refreshed by the server while a client is connected, so a long network drop doesn't lock someone out — refreshed tokens last ten minutes or the remainder of the original, whichever is longer — and they're re-issued automatically when a participant's name, permissions, or metadata change. And token revocation, which invalidates a participant's existing token when you remove them or change their permissions, is Cloud only. Self-hosted deployments have no revocation; the documented mitigation is short TTLs and not re-issuing tokens for someone you've just removed. That's a real, quotable difference between the two deployment models and one of the few places where self-hosting is straightforwardly weaker on security.

The PII trap, twice

Participant identity and room name are recorded in logs and traces throughout LiveKit's infrastructure and are not removed by PII redaction. Use opaque UUIDs and map them in your own backend. This is the same trap as the individual SIP dispatch rule that names rooms after phone numbers — one warning, two places it bites. For a healthcare or financial customer, raise it unprompted; it lands as competence rather than as a problem.

10

Shipping it and watching it

Deployment on Cloud is deliberately unglamorous. A livekit.toml in your repo describes the deployment; lk agent deploy uploads your build context (1 GB cap — use .dockerignore), builds a container from your Dockerfile, and rolls it out. There's a GitHub Action if you'd rather deploy from CI, with an optional Slack notification and the usual environment-with-required-reviewers trick for manual approval.

The rollout is where the voice-specific thinking shows. New instances come up alongside the old ones; traffic only moves once the new instance's health check passes, with a five-minute allowance (so a prewarm that takes longer than five minutes will quietly prevent your deploy from taking effect). Old instances then stop accepting new sessions but stay alive for up to an hour to finish the calls they're already on. Nobody gets hung up on mid-sentence because you shipped. On self-hosted Kubernetes you get the same behaviour by setting terminationGracePeriodSeconds generously — the docs suggest ten-plus minutes for voice — because agent servers drain on SIGTERM rather than dying.

Rolling back is a single command with no rebuild, and it drains the same way. It's a paid-plan feature; on the free plan you revert your code and redeploy.

Cold starts

On the free Build plan, production agents scale to zero after the last session ends, and the next caller waits 10 to 20 seconds for the agent to join. Paid plans (Ship and Scale) keep agents warm. Non-production deployments always scale to zero on every plan. If a prospect pilots on the free tier and reports "it takes forever to answer," this is almost certainly why — and it's a pricing artefact, not a product one.

Agent deployments are region-scoped: currently us-east (Ashburn), eu-central (Frankfurt), and ap-south (Mumbai). One deployment lives in one region, but you can deploy the same agent to several. Cloud also applies geographic affinity when dispatching, preferring to match a user with an agent server near them.

Observability

This is a genuinely strong part of the product and it's the one that separates a demo from something you'd run a contact centre on. Cloud's agent insights give you, per session, a unified timeline of turn-by-turn transcripts, OpenTelemetry-style traces broken into spans for every pipeline stage with token counts and durations attached, runtime logs from the agent server, and an audio recording of the actual call — collected locally and uploaded when the session ends. Tool calls and handoffs appear inline, so you can see the exact moment the model chose wrong.

Four operational details. Traces stream live while the session runs; transcripts and recordings upload afterwards. If noise cancellation is on, the recording is post-cancellation — you hear what the STT heard, which is the right choice for debugging. Retention is 30 days, full stop, on every plan; if a customer needs seven years of call recordings for compliance, that's egress writing to their own bucket, not observability. And observability only works when your media is on Cloud — it works for self-hosted agents connected to Cloud media servers, but not with self-hosted media servers.

Around that sit log drains to Datadog, CloudWatch, Sentry, New Relic, Splunk, Google Cloud, or syslog — necessary because session logs only cover things that happen inside a session, and crashes, startup failures and dispatch errors happen outside one. OpenTelemetry export for sending traces to Langfuse or anywhere else. And PII redaction, off by default, bundled at no extra cost, applied before storage, with a sensible one-way override: a session can force redaction on even when the project setting is off, but can never turn it off for a project that requires it.

Read this one out loud to a free-tier prospect

Projects on the free Build plan are enrolled in LiveKit's model improvement program — some anonymised session data may be retained beyond 30 days to improve models such as the turn detector. Paid plans (Ship, Scale, Enterprise) are excluded and their data is fully deleted after 30 days. This applies to observability data only; models called through LiveKit Inference are zero-retention on every plan.

What the plans gate

Four tiers: Build (free), Ship (from $50/mo), Scale (from $500/mo), Enterprise (custom, annual commitment so LiveKit can pre-provision capacity). Almost everything is metered on top with an included monthly allowance; on the free tier the allowance is a hard cap and requests simply fail past it, while paid tiers bill overage. Allowances reset monthly and don't roll over.

You will not be asked to recite prices. You may well be asked "can we have X?", and the useful thing is knowing which line X sits above.

Reading down that table, the shape of the business is obvious. Scale is the compliance tier. A couple of other numbers that shape a POC: the free tier includes 1,000 agent session minutes, 5,000 WebRTC participant minutes, 1,000 third-party SIP minutes, one free US local number with 50 inbound minutes, $2.50 of inference credit (roughly 50 minutes of conversation), and 100 concurrent participants. That is enough to build something real and nowhere near enough to pilot with actual customers, which is presumably the intent.

Do the arithmetic once

The pricing calculator's own worked example for a phone call on Build/Ship comes to roughly $0.067 per minute all-in: $0.010 agent session, $0.010 telephony, $0.010 observability, plus inference at about $0.037 (with TTS at $0.030 dominating). Two things fall out. TTS is over half the model cost, so voice selection is a cost decision as much as a brand one. And observability is a line item — real value, but not free, and worth naming rather than letting a customer discover it on an invoice.

Self-hosting, honestly

The open-source path is real, not a trap, and you should be comfortable recommending it when it fits. A single LiveKit server node has no external dependencies at all. Add Redis and it becomes a distributed cluster: nodes report stats to Redis, become aware of each other, and route so that everyone in a room lands on the same node. Egress, Ingress and SIP each deploy as separate services, also coordinating over Redis. Agents run as containers on Kubernetes or anything similar, registering outbound to your server.

What you give up is specific and the docs are unusually candid about it.

The middle three rows are where most of the real cost sits. Losing managed hosting means you own autoscaling for a workload whose sessions last minutes rather than milliseconds — the docs give useful guidance here (scale up at a lower threshold than your load_threshold, shorten scale-up cooldowns because voice load spikes are sustained, lengthen scale-down cooldowns because draining takes time), but it's still your problem. Losing observability means building a transcript-and-trace pipeline from OpenTelemetry hooks, which is weeks of work you weren't planning. And losing Krisp meaningfully degrades telephony transcription quality.

Note also that agent observability works for self-hosted agents as long as your media is on Cloud — so a hybrid where the agent runs in the customer's VPC and the media rides Cloud is a supported, documented middle position. That's frequently the right answer for a customer whose objection is really "our code must run in our account."

Keep this one

Self-hosting is the right recommendation when the constraint is regulatory or contractual — data must not leave our infrastructure, full stop — and when the scale is modest and single-region. It's the wrong recommendation when the customer wants global low latency, elastic scale, or a short time to production, because they will end up rebuilding the mesh, the autoscaler, and the observability stack themselves. Say which one you think they are, and why.

CODA

What I'd be ready to say, and what I wouldn't

Ten facts that survive contact with a whiteboard, and are specific enough to signal that you've actually read the documentation rather than the landing page:

  • Cloud is a multi-home mesh, not a managed single-home server. A session spans data centres; each participant connects to the nearest edge; failures are handled by ICE-restart live migrations in under a second.
  • Dispatch is under 150 ms; a vanished agent is replaced in about 15 seconds; every job runs in its own process.
  • Rolling deploys drain for up to an hour so live calls finish. Nobody gets cut off by a release.
  • The docs recommend the STT-LLM-TTS pipeline as the production default — for auditability, tool-calling maturity, live transcripts, and scripted speech.
  • LiveKit Inference is zero data retention by default, on every plan, with no configuration.
  • Krisp runs at the SIP trunk on Cloud, cleaning phone audio before STT ever sees it.
  • Warm transfer keeps the caller's session alive and can fail back to the agent. Cold transfer is a SIP REFER and is one-way.
  • Egress is a first-class recording product with five shapes and a real audio-only cost saving.
  • Observability retention is 30 days, always. Long-term retention is an egress-to-your-bucket design.
  • Scale is the compliance tier — SOC 2 reports, HIPAA BAA, RBAC, region pinning.

And the things to say "I'd check" about, because pretending otherwise is how credibility dies:

  • SIP gaps. No REGISTER, no SIPREC, no video over SIP. If their recording compliance runs on SIPREC, that needs a design conversation, not a yes.
  • LiveKit Phone Numbers is US-only and inbound-only. Outbound is "coming soon" with no date I could find.
  • Region pinning disables cross-region failover and requires LiveKit support to enable it. It's a trade, and it's Scale-plan-only.
  • Python/Node parity isn't total. MCP support, for one, is documented for Python only. Check per feature rather than assuming.
  • Model rosters churn with published retirement dates, some only weeks out. Never quote a model name from memory.
  • The mesh engineering post dates from 2022. The architecture is still the reference description, but specific numbers in it may have moved.
  • Concurrency ceilings above Scale are negotiated, not published — Enterprise requires an annual commitment so capacity can be provisioned ahead.
  • I could not find published detail on SLA remedies (what 99.99% actually entitles you to), on ISO 27001 or GDPR beyond a "standard DPA" line, or on on-prem/private deployment terms beyond "contact sales."
The move

In a pre-sales conversation, the person who names the limit before the customer finds it is the person the customer believes about everything else. There are eight limits on this page. Use one or two, unprompted, at the moment it's relevant — and then say what you'd do about it.
