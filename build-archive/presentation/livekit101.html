01

LiveKit is three layers, not one product

When people say "LiveKit," they're usually pointing at one of three different things without realizing it. Untangling them is most of the battle, so let's name all three up front and then take each in turn.

So there are really four things wearing the same name, and keeping them straight is the whole game:

When someone says "LiveKit"They might mean
the media serverthe open-source Go program that routes audio. The foundation.
the room modelthe concepts — rooms, participants, tracks — that everything is built around.
the Agents frameworkthe Python/Node library you use to write an agent.
LiveKit Cloudthe managed product that runs all of the above for you.
Start at the bottom

Everything rests on the media server, so that's where the understanding has to start. It's the one piece that's genuinely LiveKit's, always.

02

The media server: the beating heart

At the very bottom is a single program, written in Go, that you can find on GitHub and run yourself. Its entire job is to move audio and video between people in real time. It's called an SFU — a Selective Forwarding Unit — and the name is a literal description: it selectively forwards streams.

Here's what it does, concretely. Everyone in a call sends their audio up to this server once. The server looks at who wants to hear whom, and forwards each stream down to the right people. It never opens the audio up, mixes it, or re-encodes it — it just routes, like an intelligent switchboard. That's why it adds almost no delay, and why every voice stays separate and clean.

This is the piece that is always LiveKit's, in every deployment, no matter what. Whether you're on their cloud or running everything yourself, this SFU is what the audio flows through. It is the one non-negotiable.

A fact worth having

The media server is a single Go binary you can run in Docker or Kubernetes. That's what "self-hosting LiveKit" means — running this program on your own machines. It's open source and free. What you'd be giving up by doing that is the subject of chapter 07.

But a server that moves audio needs a way to describe who's talking to whom

That's the layer above it — a small set of nouns that the whole system is organized around.

03

The room model: three nouns

The media server organizes everything around three concepts, and they are the entire data model. Once you have these, you can describe any LiveKit application.

  • A room is one session — one conversation. It exists while people are in it and closes when they all leave.
  • A participant is anyone or anything in the room. A person in a browser. A phone caller. An AI. A recorder.
  • A track is one stream of media a participant is sending — their microphone audio, say. Participants subscribe to each other's tracks to hear them.

The word doing all the work is anything in the definition of participant. The server does not care what kind of thing a participant is. A human and an AI join in exactly the same way, publish tracks in exactly the same way, and are heard in exactly the same way. That single fact is what makes the next chapter possible — and it's the fact that clears up your confusion.

Keep this one

A participant is anything that joins a room. The server treats a person and an AI identically. Hold onto that — the entire mystery of "what is an agent" dissolves the moment you accept that an AI is just another participant.

04

What an agent really is

This is the chapter that fixes the confusion, so let's be very precise. Here is the definition, taken almost word for word from LiveKit's own documentation:

The definition, verbatim in spirit

"The Agents framework lets you add any Python or Node.js program to LiveKit rooms as full realtime participants."

Read that twice. An agent is not a special LiveKit object. An agent is a program you write — an ordinary Python or Node program — that uses LiveKit's library to join a room as a participant. That's it. That's the whole thing.

The mistake almost everyone makes, and the one you made, is hearing "agent" and picturing something that lives inside LiveKit — a backend service that LiveKit hosts and runs. It's the opposite. The agent is your code, and it reaches into a LiveKit room from wherever it happens to be running.

The cleanest analogy is a library you already know. When you write a Python script that uses the AWS SDK, your script doesn't "run inside AWS." It runs on your machine and makes calls to AWS. The LiveKit Agents framework is the same shape: it's a library your program imports so it can join a room. Your program runs where you run it. The room is in LiveKit. They connect over the network.

You proved this yourself today without noticing. Your agent.py ran on your MacBook, and in the logs it said registered worker … url: wss://…livekit.cloud. Your program, on your desk, reached out to a room in LiveKit. The agent was never inside LiveKit. It was on your laptop, connected to LiveKit.

And here's the lovely part

Because the framework just adds "any program" to a room, an agent doesn't even have to be AI. LiveKit calls these programmatic participants — a recorder, a media processor, a bridge to some external system. An AI voice agent is the most common kind, but the framework underneath is simply "let my code be a participant."

05

Worker, job, session, dispatch

Now that "an agent is a program that joins a room" is solid, the rest of the vocabulary is just the machinery that connects one program to many calls. These four words appear all over the docs and your logs, and they're simpler than they sound.

WordWhat it actually is
workerYour agent program, running and waiting. It registered with LiveKit and stands by for work. One worker handles many calls. This is the thing that printed registered worker in your logs.
jobOne instance of the work — one call. When a room needs an agent, LiveKit hands the worker a job, and the worker forks a separate process to run it. Your t3.small could hold several jobs at once, each isolated.
dispatchThe act of assigning a job to a worker. Happens automatically when someone joins a room, or explicitly via API — it's what a phone dispatch rule triggers.
entrypointThe function in your code that runs for each job. "The bulk of the code and logic you write." Your my_agent(ctx) function is the entrypoint.
sessionThe AgentSession object you create inside a job — it wires up the STT→LLM→TTS pipeline and runs the actual conversation. One session lives for one call, and closes when the last person leaves.

Put together as a story: your worker starts up and registers. A customer calls. LiveKit dispatches a job to your worker. The worker forks a fresh process and runs your entrypoint, which creates an AgentSession that holds the conversation. The customer hangs up, the session closes, the process exits. The worker is still standing by for the next one.

The reliability numbers hiding in here

If a worker dies unexpectedly, LiveKit notices within about 15 seconds and dispatches a replacement. On deploy, workers drain — they finish their active calls and refuse new ones, so a restart never kills a live conversation. These aren't trivia; they're the answers to "what happens when it breaks."

06

Why Agent Builder just worked

Now the specific thing that threw you. You opened Agent Builder in the browser, filled in a form, hit a button, and talked to a working agent — no laptop, no cloud of your own, nothing installed. If an agent is "your program running somewhere," where was that program running?

The answer, straight from the docs: Agent Builder deploys your agent directly to LiveKit Cloud. The form you filled in generated the Python code for you, and the "Deploy" button ran that code as a worker on LiveKit's own infrastructure.

So the program still exists, and it's still "your code joining a room as a participant" — it's just that LiveKit is running it for you, in their data center, instead of you running it on your laptop or your cloud. Nothing about the model changed. Only the location did.

This is the third home from the previous primer, made concrete. Remember there are exactly three places your agent-program can run:

The thing that was confusing you, resolved

Agent Builder didn't prove that "the agent lives inside LiveKit." It proved that LiveKit will run your agent-program for you if you want. The agent is still a program joining a room — LiveKit just happened to be the one running it that time. Same model, hosted floor.

07

Cloud versus self-hosting

Since the media server is open source, you could run the entire stack yourself — the SFU, the coordination, the scaling, all on your own machines. So what does LiveKit Cloud actually give you that self-hosting doesn't? This is a real pre-sales question, and the honest answer is "a lot of operational weight you'd otherwise carry."

ConcernSelf-host the OSS serverLiveKit Cloud
The SFUyou run the Go binary on your machinesmanaged, you never see it
Scaling past one serveryou set up Redis coordination and a mesh yourselfa global mesh; each user hits the nearest edge, automatically
A server or region failingyour problem to detect and recoversessions migrate to another instance automatically
Running the agentyour own Kubernetesone-command managed hosting, autoscale, instant rollback
Modelsbring your own keys, wire up each providerLiveKit Inference — models with no keys, co-located for latency
Phone numbersset up carrier trunks yourselfLiveKit Phone Numbers, provisioned in the dashboard
Seeing what happenedbuild your own logging/tracingtranscripts, traces, recordings in the dashboard
Uptimewhatever you can engineera 99.99% target on redundant infrastructure

The single sharpest difference is the mesh. A self-hosted deployment is usually single-home: a given call lives entirely on one server, and everyone in it must connect to that one server no matter where they are in the world. LiveKit Cloud is multi-home: the servers form a mesh, each person connects to the edge nearest them, and the mesh relays between them. That's what makes it both low-latency everywhere and resilient to any single server dying.

Why anyone self-hosts anyway

One reason, mostly: the media itself must never touch a third party — a hard data-residency or sovereignty rule. Then you self-host the media server too, and give up the mesh, the managed scaling, and the observability to get it. It's a real tradeoff, not a free choice, and naming what they'd lose is the honest way to have that conversation.

Say it like this

"The media server is open source, so you can run all of this yourself. What Cloud buys you is the hard part: a global mesh so every user hits a nearby edge, automatic failover when a server dies, managed agent hosting, and the observability. You'd self-host the media server only if a regulation says the audio can't leave your infrastructure — and then you're taking on the mesh and the scaling yourself, which is a real cost worth being clear-eyed about."

08

The whole thing on one page

Here it is assembled, with every piece in its true home. Read it once from the left and the confusion should be gone for good.

That's the architecture, whole. The people are on the left. The room and the models are LiveKit's. The agent is your program, joining the room from wherever it lives. And behind the agent is your data and your other systems, which are entirely yours. Nothing on the right ever moves to the left — LiveKit is transport and models, and everything that knows your business stays with you.

The five sentences that hold it all

The media server moves the audio and is always LiveKit's. A room is one conversation; a participant is anything in it. An agent is your program that joins a room as a participant — it is not a thing inside LiveKit. It runs in one of three places, and Agent Builder simply picked "LiveKit Cloud" for you. And LiveKit Cloud is the managed way to run all of it, versus self-hosting the open-source server yourself.
