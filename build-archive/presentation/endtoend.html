01 · Access

How a user gets in — two connections, not one

Say this first, because it's the thing everyone gets wrong: a user makes two separate connections, over two protocols, to two different places. Keeping them apart is the key to reading the whole system.

Why a token server at all? Because a room token is signed with your LiveKit API secret, and that secret can never live in a browser — anyone could grab it and mint their own. So a small server holds the secret and hands out short-lived, scoped tokens. That's the only reason the "Web app + token" box sits on the critical path.

The load-balancer question, answered

The web app sits behind a load balancer (Cloud Run's built-in front end, or an explicit HTTP(S) LB + Cloud CDN for a custom domain). But that LB only ever fronts path 1 — web and token traffic. The voice in path 2 goes browser-straight-to-LiveKit and never touches your load balancer. Confusing the two is the classic tell that someone hasn't built this.

02 · Primers

The vocabulary you need first

Before the architecture makes sense, four words have to be concrete: token, room, participant, track. Here's each in a paragraph — verified against LiveKit's own docs — so nothing downstream is hand-wavy.

Primer 1 · the one you asked about

The access token — your key to the room

To join a room, a client must hand LiveKit an access token. It's a JWT — a small signed blob of JSON — signed with your LiveKit API secret so it can't be forged. It encodes who you are, which room you may enter, what you're allowed to do there, and when it expires. That's the whole "what kind of token" answer: not a password, not an OAuth token — a short-lived, self-describing permission slip your server signs.

Here's a real decoded one (this is the exact shape from LiveKit's docs):

{
  "iss": "APIMmxiL8rqu…",   // your API key — identifies who issued it
  "sub": "user-7f3a",       // participant identity — use a UUID, never a real name
  "exp": 1621657263,      // expires — gates the FIRST connect only, not reconnects
  "video": {
    "room": "support-42",  // which room this token is good for
    "roomJoin": true,     // may join it
    "canPublish": true,   // may send its microphone audio
    "canSubscribe": true  // may hear the agent
  }
}

The permissions live in the video grant. For a voice call the four that matter are roomJoin + room (join this room), canPublish (send mic audio), and canSubscribe (hear the agent). There are more — roomAdmin, canPublishData, a separate sip grant for telephony — but those four get a browser talking to an agent.

Who mints it
Your token server (the web app on Cloud Run) — because it holds the API secret. Never the browser; a leaked secret lets anyone forge tokens into your rooms.
How long
Short-lived — you set the TTL. Expiry only blocks the initial connect; once joined, a mid-call reconnect isn't kicked out.
Summoning the agent
You can bake RoomConfiguration(agents=[RoomAgentDispatch(agent_name="…")]) into the token — that's how a browser's join token also tells LiveKit which named agent to dispatch into the room.
PII rule
Identity and room name land in logs and traces unredacted — put an opaque UUID there, and map it to the real customer in your own backend.
Primer 1½ · a REAL token from the running system

Watch the token get made — end to end

This isn't a textbook example — it's an actual token this build minted, decoded live. Here's the full round trip.

① The browser asks the web app for a token — one HTTPS call, on page load:

GET https://aug24-web…run.app/token
→ { "token": "eyJ…", "url": "wss://…livekit.cloud", "room": "web-7deb67a2" }

② The server mints it — holding the secret the browser never sees:

identity = f"caller-{uuid4().hex[:6]}"          # opaque UUID — no PII
grant = VideoGrants(room_join=True, room=room,
                    can_publish=True, can_subscribe=True)
rc = RoomConfiguration(                       # summon the named agent
        agents=[RoomAgentDispatch(agent_name="anycompany-agent")])
jwt = (AccessToken(KEY, SECRET)               # SECRET signs it — server-side only
       .with_identity(identity).with_grants(grant)
       .with_room_config(rc).with_ttl(15 min)).to_jwt()

③ What that token actually contained — decoded from the real JWT:

{
  "sub":   "caller-436977",        // identity — a UUID, not a name ✓
  "iss":   "APIJbdxTYB25y4B",     // your API key (the public half)
  "video": {
    "roomJoin": true,           // may enter
    "room": "web-7deb67a2",      // THIS room only
    "canPublish": true,         // may send mic audio
    "canSubscribe": true        // may hear the agent
  },
  "roomConfig": { "agents": [{ "agentName": "anycompany-agent" }] },
  "nbf": 1787667175,             // valid-from
  "exp": 1787668075              // expires — exactly 900s = 15 min later
}
— signed: HMAC-SHA256(header.payload, SECRET)  ← makes it unforgeable

④ The browser connects with it — token in hand, straight into LiveKit over WebRTC:

const { token, url } = await fetch('/token').then(r => r.json());
await room.connect(url, token);   // becomes a participant; agent is dispatched

That's the entire "how does a user get in." The customer clicks Start call and sees none of it — the page fetches the token and connects. The roomConfig.agents line is the quiet magic: it's how a browser's token also tells LiveKit to pull your agent into the room, with no separate signaling.

Primer 2 · the data model

Room, participant, track

Three nested ideas, and once they click the whole system reads cleanly:

Room
The session container. Everything happens inside exactly one room — it's the thing the token grants you into.
Participant
Anyone or anything in the room: the caller, the agent, a human specialist, a phone caller over SIP. Each carries a kind — standard, sip, agent. This is why "the agent is a participant, not a backend" is literally true: it joins with kind: agent.
Track
A live media stream a participant publishes. The caller publishes their microphone track; the agent publishes its synthesized-voice track; each subscribes to the other's.

So "join the room" unpacks to: present a token with roomJoin → become a participant → publish your mic track and subscribe to the agent's voice track. That one sentence is the entire connection.

Primer 3 · why this transport

Why WebRTC, not a WebSocket

Voice needs low latency and tolerance for lost packets. WebRTC runs over UDP with the Opus codec, a jitter buffer, and packet-loss concealment — so a dropped packet becomes a tiny, inaudible glitch rather than a stall. A WebSocket rides TCP, which retransmits lost packets and head-of-line-blocks behind them, adding delay you can actually hear in a conversation. That's why the voice path (path 2) is WebRTC while the page-load and token path (path 1) is ordinary HTTPS.

Primer 4 · the firewall question — you WILL get asked this

How the connection punches through NAT & corporate firewalls

"Will this work inside our locked-down enterprise network?" is a top-three real customer question, and WebRTC has a specific answer: ICE. When a client connects, ICE probes every possible path and uses the best one that works, in this priority order:

STUN
A quick lookup that tells the client its own public IP behind the router, so a direct UDP path can be tried first (the fastest). LiveKit clients use Google's public STUN by default.
Direct TCP
If UDP is blocked, fall back to a direct TCP path.
TURN relay
If both direct paths fail — symmetric NAT, a strict corporate firewall — media is relayed through a TURN server. Crucially, TURN over TCP on port 443 looks exactly like HTTPS, so it slips through nearly every corporate firewall.

The honest number to know: in managed corporate environments, 60–70% of connections end up on TURN relay rather than direct. So the answer to the firewall question is: "yes — it degrades to a TURN relay on 443 that's indistinguishable from web traffic, and LiveKit Cloud runs that relay layer for you."

API key vs secret — don't mix them up

Your project has an API key (a public identifier — it appears in the token as iss) and an API secret (the private signing key). The key can be public; the secret signs tokens and lives server-side only. If someone asks "how is the browser trusted," the answer is: it isn't — your server proves trust by signing the token with the secret, and the browser just carries the result.

03 · Architecture

The full architecture

Here it is whole, with every component in its real home and every kind of traffic drawn distinctly — including the human handoff. Read it left to right: the user, the two entry paths, LiveKit in the middle, your GCP on the right, and the specialist who can join the same room.

Why RAG isn't called from LiveKit — the question Mike will ask

LiveKit is the media plane: it moves audio and runs the models. It is a third-party managed service and never touches your data. The agent is your code, the brain — it's the only thing that knows about your business systems. So the chain is: the LLM decides "I need a knowledge lookup" and emits a tool call → the agent (running in your GCP, with your IAM) executes it → agent → MCP → Vertex RAG. LiveKit is never in that path. You'd never hand a media vendor direct credentials to your corpus; the agent, inside your trust boundary with Workload Identity, is where the media plane and your data plane meet.

05 · Construction

How to build it — the order that de-risks

You don't build this as one big bang. You build it as a sequence where each step is independently runnable, so a failure is always localized to the thing you just added. This is also the order to describe it in.

  1. Bare agent, talking

    Scaffold the LiveKit Agents Python project, wire STT→LLM→TTS against LiveKit Inference, talk to it in the console. No GCP yet — prove the loop.

    uv run python src/agent.py console

  2. Measure it

    Turn on per-turn metrics and capture your own latency against the published budget — so you quote real figures, not doc numbers.

  3. Data + direct tools

    Firestore with orders and customers; function tools for the every-call reads. These stay direct — the hot path.

  4. The MCP boundary

    Put ticket writes and knowledge search behind an MCP server on Cloud Run; wire the agent as an MCP client. Now the "external boundary" is real.

  5. RAG for knowledge

    Ingest the policy PDF into a Vertex RAG corpus; expose search_knowledge via MCP. Verify with a document-unique question.

  6. Web app + token server

    A minimal page + token endpoint on Cloud Run that mints a scoped token and dispatches the named agent. Now a browser can call.

  7. Move the agent to GKE

    Containerize; deploy with a 600s grace period paired to the worker drain — a deploy never drops a live call. Private nodes + Cloud NAT.

    terminationGracePeriodSeconds: 600 · --drain-timeout 600

  8. Then the -ilities

    Only once it runs end to end: fallbacks, multi-region, observability, load testing. Happy path first; harden second.

06 · The model layer

The model layer — the choice that defines the product

Three models sit in the pipeline, and the biggest architectural decision in the whole system is whether they stay three separate models (cascaded) or collapse into one (speech-to-speech). This is where a principal SE earns the room.

STT — speech to text

Transcribe + endpoint

Streams partial transcripts as the user speaks. Pick on domain accuracy and first-partial latency. A fallback vendor covers a provider brown-out.

LLM — the brain

Reason + call tools

Decides what to say and which tool to fire. Bigger = smarter but slower first token. Size to the task; a faster model is your retry target under load.

TTS — text to speech

Speak it back

Streams audio from the first words, so the user hears speech before the sentence finishes. Voice quality and time-to-first-audio are the levers.

Turn detection

Has the user finished?

A semantic end-of-turn model plus VAD — VAD hears speech presence and drives barge-in; the model decides the turn is actually done. Both, not either.

STT · LLM · TTS — how each stage actually works

The cards above name the three stages; here's what each one does, the one metric that matters, and the model your build actually runs. The through-line: every stage streams, and streaming is what makes three sequential models close the loop in under a second.

Stage 1 · the ears

STT — speech to text

Turns the caller's audio into text live, without waiting for them to finish. For each segment it emits a stream of transcripts in three flavors:

interim
preliminary, updates as more audio arrives, no formatting — for real-time captions.
final
the STT is confident this text won't change.
preflight
stable enough to act on before it's final — the hook that enables preemptive generation (below).

Metric that matters: word-error-rate on your vocabulary + first-partial latency. Your model: assemblyai/universal-3-5-pro. Gotcha: numbers, names, acronyms, accents, noise — exactly the class of the order-number-digit bug.

Stage 2 · the brain

LLM — the model

Takes the transcript + history + system prompt + tool definitions and decides what to say and whether to call a tool. It streams tokens as it generates, so TTS can start speaking before the reply is finished. When it needs data it emits a structured tool call, the agent runs it, feeds the result back, and the model continues grounded in that result. You can even scope which tools are callable per reply (e.g. surface a payment tool only at checkout).

Metric that matters: TTFT — time to first token (target < 800 ms). Your model: google/gemma-4-31b-it, voice-tuned. Gotcha: it hallucinates (why RAG exists), it's untrusted (authorization never lives in the prompt), and the prompt must force short, speakable replies — no markdown, no bullet lists.

Stage 3 · the mouth

TTS — text to speech

Turns the reply into spoken audio in your chosen voice, streaming from the first words so the caller hears speech ~100–300 ms after the model starts. If a TTS model can't stream natively, LiveKit splits the text with a sentence tokenizer and synthesizes incrementally. Expressive models also render inline delivery markup (emotion, pacing) the model emits — which never shows in the transcript.

Metric that matters: TTFB — time to first byte of audio + naturalness. Your model: fishaudio/s2.1-pro (renders the expressive markup). Gotcha: pronouncing names/numbers, sounding natural, and stopping cleanly on barge-in.

The advanced latency trick — preemptive generation

Here's the move that impresses: the pipeline doesn't have to wait for end-of-turn to start thinking. On a stable preflight transcript, LiveKit speculatively runs the LLM before the turn is confirmed, so the reply is ready the instant the caller actually stops — and preemptive_tts can speculatively run TTS too. It hides real latency behind the last moment of the caller's speech. Combined with streaming and co-location, this is how "three models in a row" still feels instant.

Turn detection & barge-in — LiveKit's crown jewel

This is the piece competitors don't have, so know it cold. The problem: knowing when the caller has actually finished speaking. A pause isn't the end of a thought — "I need to think about that for a moment…" then silence would make a naive system barge in. LiveKit solves it with two layers working together:

VAD
Voice Activity Detection (Silero) — hears whether there's speech present right now. Fast and dumb: it drives the barge-in trigger, but on its own it mistakes a thinking-pause for a finished turn.
Turn model
An open-weights end-of-turn model — fine-tuned from Qwen2.5-0.5B, distilled from a larger teacher so it runs low-latency on CPU. It reads the semantic content ("did they finish a thought?"). A newer audio variant also reads intonation, pitch, and rhythm directly from the waveform — how it was said, not just what.

The result is measurable and it's the number to quote: at a 300 ms budget the model hits a 9.9% false-cutoff rate vs 12.9% for Deepgram Flux and 27.7% for a VAD-only approach — i.e. it interrupts people far less often at the same speed. That's the false-cutoff-vs-latency dial: tighten the threshold and you respond faster but talk over people; loosen it and you feel slow. You tune it to the use case.

Barge-in — how interruption actually works

When the caller talks over the agent, three things must happen immediately: turn detection stays live during playback (not just when the agent is silent), the current TTS stream is cancelled and its audio buffer flushed, and control hands straight back to the STT pipeline. Get this right and the agent feels human; get it wrong and it steamrolls the customer. It's the single most-felt piece of conversational UX — worth saying you'd tune it explicitly.

When to recommend which

  • Cascaded (what this build uses) — when you need per-component failover, a clean transcript for logging and eval, tight control over each stage, and freedom to swap a vendor without touching the rest. The default for contact-center work.
  • Speech-to-speech — when natural prosody and the lowest latency matter more than control: a companion, a demo, a premium consumer experience. You trade the transcript and the failover for feel.
  • Half-cascade — the in-between — a realtime model does the listening (so it hears tone and emotion) but a separate TTS speaks the reply (so you keep script control and a stable voice). Choose it when you want realtime's ear but a pipeline's mouth. LiveKit runs all three behind the same room, so the choice isn't religious — pick per use case, change your mind without re-architecting.

Which model when — pick by what the use case can't compromise

Every model choice is really the same dial: quality vs speed vs cost. Because the pipeline is cascaded, you set that dial per stage — a fast STT, a mid LLM, a premium voice — instead of one global setting. Here's how that lands in real scenarios, with the models LiveKit Inference actually serves:

07 · Tools

Function tools vs MCP — and when to use which

"Tools" are how the LLM reaches out of the conversation to do something — look up an order, file a ticket, search knowledge. LiveKit gives you three ways to attach them, and knowing which to reach for is a real design signal.

1 · function tools

Defined in your agent code

A Python function with a @function_tool decorator, running in-process with the agent. Lowest latency, full control, but it ships and versions with the agent — change it, redeploy the agent.

2 · MCP servers

A separate tool service

Tools live in their own service; the agent connects and fetches the tool list at startup. Adds a network hop, but the tools are independently deployable and shareable across agents.

3 · provider tools

Built into the LLM

Server-side tools the model runs inside a single API call — web search, code execution, file search (OpenAI, Gemini, xAI). Zero infra on your side; you just enable them.

the guardrail

max_tool_steps

Caps consecutive tool calls per turn (default 3). Hit the cap and the agent makes one final call with tools disabled to speak a summary — stops runaway tool loops.

Which to choose — the decision

Reach forWhenWhy
Function tool (direct)hot-path, every-call reads tightly coupled to this agent — order status, warranty checklowest latency, no extra hop; the tool only this agent needs
MCP serverthe genuinely external systems, tools shared across agents, tools owned by another team, or tools that change on their own release cadenceindependent deploy (change the tool without redeploying the agent), one place for retry logic, reuse — worth the hop
Provider toolgeneric capabilities the model already has — web search, code execzero infrastructure; nothing to build or operate

That's exactly the split in this build: lookup_order and warranty checks are function tools on the hot path, while ticket-writing and knowledge search sit behind MCP — because they're the real external-system boundary, they carry the retry logic, and the MCP server can be redeployed (a new knowledge corpus, a changed ticket schema) without ever touching the agent.

Say it like this

"I don't put everything behind MCP. Every-call reads like order lookup are direct function tools — in-process, no extra hop. I reserve MCP for the genuinely external systems: ticketing and knowledge. That boundary buys me three things — one place for retry logic, reuse across agents, and independent deploys, so I can swap the knowledge corpus or the ticket schema without redeploying the agent. And anything generic like web search I'd just enable as a provider tool rather than build at all."

08 · Request lifecycle

One request, end to end

Trace a single question — "how quickly do I have to report a damaged device?" — from the user's lips to the spoken answer. The voice never enters GCP; only the tool call does.

  1. User clicks "Start call" → browser fetches a room token from the web app (Cloud Run). The token is signed with the LiveKit secret and dispatches the named agent.
  2. Browser opens WebRTC to the LiveKit room. LiveKit dispatches a job to the agent worker on GKE, which joins the room as a participant.
  3. User speaks. STT streams a transcript; the turn-detection model decides the user has finished.
  4. The LLM decides to call search_knowledge — a policy question, so it must look it up rather than guess.
  5. The agent (GKE) sends an MCP request to the MCP server (Cloud Run), which calls Vertex RAG retrieveContexts, gets the top passage from the return-policy corpus, and returns it.
  6. The LLM composes an answer grounded in that passage → TTS → back into the room → the user hears "within 48 hours of delivery."
Verified live — the two-part proof

The MCP logs on this exact turn show TOOL search_knowledge('how quickly do I have to report a damaged device?') → RAG then RAG retrieved 1 passages from Vertex corpus. The tool firing proves the path executed; the answer "48 hours" — a fact that exists only in your PDF — proves it grounded on your document, not the model's memory. That's how you prove RAG both ways.

09 · Latency

Latency optimization — the LiveKit-specific levers

The target is under one second from the user finishing to the agent starting — roughly human conversational timing, so past it the agent feels broken. Here's the budget and the numbers you measured.

StageBudgetLever
Audio transport to edge< 50 msLiveKit's nearest-edge mesh — free
End-of-turn decision~300 msthe biggest slice — tune the turn-detector per use case
LLM first token200-400 msmodel size; a tool call adds a round trip
TTS first audio100-300 msstreaming synthesis — speak before the sentence ends
Your MCP → Firestore tool call~55 msmeasured, server-side
  co-located hop (agent + MCP same region)~4 msmeasured — vs ~70 ms cross-country

The five levers, in order of impact

  • Co-location is the biggest structural lever. You measured it: agent (GKE) in the same region as the MCP server dropped the tool hop from ~70 ms to ~4 ms. Agent, models, and data share a region; the region sits near the users. A mismatch is a transatlantic hop per turn.
  • Align the LiveKit region with the GCP region. LiveKit inference and your agent in matching geography, or every turn pays the gap twice — audio out and audio back.
  • Tune the turn-detector, don't just accept it. The end-of-turn decision is the biggest single slice. Too eager cuts the user off; too patient feels slow. A dial you set to the use case.
  • Keep the hot path direct; reserve MCP for the boundary. Every-call lookups are direct tools; ticketing and knowledge go through MCP. Common path fast; boundary earns its hop.
  • Cover slow work with speech. A slow tool call gets a spoken "let me pull that up" and progress updates — perceived latency, not just measured latency.
Say it like this

"Budget's under a second, and the biggest lever isn't model choice — it's co-location. My tool call is about 55 milliseconds of real work, but from my laptop the round trip was 130 because of the cross-country hop; co-located in the same region it dropped to about 4. So I put the agent, the models, and the data in one region near the users, keep every-call lookups as direct tools, and cover anything slow with a spoken filler so the customer never hears silence."

10 · Scale

Scale — how it grows

The number to have ready: a Python voice worker holds roughly 5 to 20 concurrent sessions per CPU core, depending on the pipeline. So it's tens of calls per machine, not hundreds — voice agents are heavy, and that shapes every scaling decision.

  • The agent (GKE) scales horizontally — more pods. LiveKit dispatch places each session on a worker by effective load, pinned there for the call's life. 500 concurrent is tens of cores across a fleet, autoscaled on active-session metrics, not CPU alone.
  • Web app + MCP (Cloud Run) scale trivially — stateless, request-shaped, scale to zero when idle. The opposite shape to the agent.
  • LiveKit Cloud scales the media plane for you — built for millions of concurrent connections.
  • Firestore and Vertex RAG are serverless — they absorb load without provisioning.

How dispatch actually places a call — and what to watch

Workers continuously exchange availability and capacity with LiveKit, so the scheduler load-balances new sessions across them. Because sessions are long-lived, it's stateful load balancing: it pins a session to one worker for the whole call and places new ones by effective load, factoring in user locality, CPU/GPU, memory, and network to keep latency and jitter low. The honest edge case: under a sharp burst, spinning a fresh worker takes time, and a new session waiting on cold capacity can see its first response stretch from a few seconds to much longer — another reason to pre-warm rather than scale reactively.

You can't tune what you don't measure. The per-turn metrics to watch continuously — LiveKit surfaces them, and its Agent Observability lets you replay a session with synced audio, transcript, and traces:

MetricIsTarget
TTFTLLM time-to-first-token< 800 ms

The honest constraint

Because agents are heavy and hold state, the agent tier has thinner headroom than a stateless web tier — you can't absorb a spike by forking a thousand workers instantly; each is a real process holding a call. For known peaks you pre-warm capacity rather than scaling reactively, and you decide explicitly what happens past the ceiling: queue, degrade, or overflow to humans.

Say it like this

"Will it hold 500 concurrent calls? The media plane, comfortably — that's LiveKit's job. The constraint is the workers: five to twenty sessions per core, so 500 is tens of cores across a GKE fleet, autoscaled on active sessions. But agents are heavy and stateful, so I'd pre-warm for known peaks — and I'd ask you whether 500 is the peak or the average, and what acceptable behavior is past the ceiling: queue, degrade, or overflow to a human."

11 · Cost

Cost & economics — where the money goes

A voice agent is billed roughly by the minute, and the cost of one minute is the sum of the pieces running during it. The principal move isn't quoting a price — it's knowing which piece dominates and which lever moves it.

Cost pieceDriven byRelative weight
LLMtokens — context length × turnsusually the biggest & most variable
TTScharacters / seconds of audio spokenmeaningful
STTminutes of audio transcribedmodest
Media transport (LiveKit)participant-minutesmodest, predictable
Agent compute (GKE)a fraction of a core-minute per callsmall
Tools · RAG · Firestoreper querynegligible per call

The five cost levers

  • Right-size each model. The LLM usually dominates, so don't pay for a giant model to read back a tracking number. Cascaded lets you pick a cheap, fast model per stage and reach for a bigger one only when the task needs it — a real cost argument for cascaded, on top of the failover one.
  • Keep context tight. The LLM bill scales with tokens, and tokens pile up every turn. Use handoffs and scoped tasks so the model isn't re-reading irrelevant history on every request — this is exactly why LiveKit pushes workflows over one giant prompt.
  • Don't pay for silence. VAD gates dead air so you're not transcribing and processing an empty channel while the caller thinks.
  • Cache the static parts. System prompts and tool schemas repeat every turn — prompt caching stops you paying to re-send them.
  • Reduce waste, not just unit price. Co-location doesn't lower the per-token price, but it cuts the timeouts and retries that quietly double a turn's cost.
The cost triangle — name it out loud

Cost ↔ latency ↔ quality pull against each other: a bigger model is smarter but slower and pricier; a snappier turn-detector is cheaper but risks cutting people off. There's no free corner — you tune the triangle to the use case. Saying this is more senior than quoting a single number.

Say it like this — and the build-vs-buy close

"Per minute, the LLM usually dominates and it scales with tokens, so I keep context tight with handoffs and right-size each model — another reason I like cascaded: a cheap fast model reads a tracking number, and I only reach for a bigger one when the task needs it. And the honest build-vs-buy point: the per-minute inference isn't the whole cost. If a customer says 'we'll just call OpenAI Realtime directly,' the hidden cost is rebuilding telephony, media scaling, turn detection, and failover themselves. LiveKit's value is renting the hard media layer so your spend goes to the agent logic that actually differentiates you."

12 · Redundancy

Redundancy & reliability — what breaks, and what the caller hears

The principal framing isn't "does it have fallbacks" — it's "when this fails at 2pm, what does the caller hear." Redundancy lives at four layers, and they fail differently.

The distinction that separates you from everyone else — media plane ≠ agent plane

LiveKit's famous resilience — session migration, self-healing SFU mesh — is media-plane resilience, and it's automatic. But your agent is a participant whose conversation state lives in one worker process. If that worker dies mid-call, the media plane is fine and the agent is gone — there's no automatic hand-off of agent state to another worker. Graceful drain protects you on deploys (planned) but not on crashes (unplanned). Saying this out loud — and proposing durable session state or fast re-dispatch as the fix — is exactly the principal-level honesty that makes an interviewer trust everything else you said.

What failsWhat the caller hears — and what you did
Deploy during a live callNothing. Graceful drain on GKE — the old pod finishes its calls before terminating (grace 600s + worker drain 600s), new calls go to the new pod. The reason the agent is on GKE, not Cloud Run.
STT / TTS vendor degradesA brief blip at most. Per-component failover to a second vendor, health-checked on latency, not just errors. The structural argument for cascaded.
LLM slow or rate-limitedSpoken filler, retry on a faster model, hard escalation if it persists. Never dead air.
An agent worker crashes mid-callThat call is dropped, not just degraded — and its conversation state is gone with the process. The SFU (media plane) survives, but the agent's context lived in that worker; a re-dispatched agent starts cold, and under load that recovery has been seen to push time-to-speak from ~5s to tens of seconds. Own this as the real single point of failure — don't claim it's free.
MCP / ticketing downNothing — the write is queued and reconciled later; the conversation never blocks. A core argument for the MCP boundary.
Region outageTraffic routes to the next region — if your GKE and data are multi-region too. Otherwise you've moved the single point of failure, not removed it.
Say it like this

"The one I design around rather than paper over is a deploy during a live call — exactly why the agent is on GKE, with a ten-minute grace period paired to the worker's drain, so the old pod finishes its calls while new ones go to the new pod. Cloud Run couldn't guarantee that. For vendor degradation I fail over per component — my main reason to stay cascaded. If ticketing goes down I queue the write instead of blocking the conversation — a big part of why that sits behind its own MCP boundary. And for a region outage I'd be honest: it only helps if the agent and data are multi-region too, otherwise I've just relocated the single point of failure."

14 · Narration

How to talk about it

The architecture is the easy half. The pre-sales half is how you narrate it. Five rules, drawn from everything above.

1. Ask before you draw

The reference diagram is a set of choices, not a template. Open with the questions that change it: where does data live, public or VPC, regulated, peak volume, existing telephony provider. Those decide where the agent runs, the database, the region, the sizing. Asking is the job, not stalling.

2. Separate the paths out loud

The clearest signal you understand the system: "voice goes browser-to-LiveKit over WebRTC; the web app and token are a separate HTTPS path; only tool calls cross into my cloud. Media plane and data plane never mix."

3. Lead with the measured lever

"Co-location beats model tuning" lands harder with a number: "130 ms from my laptop, 4 ms co-located." You built this — use it. Same with RAG: "I verified it fired against my own document with a fact only my PDF contains."

4. Own the model decision

When Mike asks about models, don't list vendors — frame the axis: cascaded vs speech-to-speech, and why cascaded fits customer service. Naming the tradeoff is more senior than naming a model.

5. Critique your own design

The most senior move is naming what's missing: no multi-region yet, RAG retrieval is coarse on a tiny corpus, no eval loop in CI. "The architecture is right; the -ilities are what separate this demo from a contact centre." That honesty gets you believed on everything else.
