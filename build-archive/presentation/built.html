03

Why Cloud Run — and when you'd move to GKE

A voice session has to stay on one instance for its whole life — you cannot move a live call to another machine. That "stickiness" sounds like it should decide the compute, so it is worth being precise about where it actually comes from.

The surprise

LiveKit provides the stickiness itself, at the dispatch layer. When a call starts, LiveKit hands the job to one worker and the session lives on that worker until the call ends — it is never re-routed. So session-to-worker affinity is handled above the cloud, which is why Cloud Run worked at all. One instance holds many concurrent sessions, each pinned where it started.

So what is left for the compute layer to get wrong? The instance lifecycle — scale-in and deploys — and that is exactly where the two options differ.

Cloud Run (what we used)GKE (production)

Best fordemo, POC, low-moderate scalea real contact centre

The one row that matters is graceful drain. On GKE you set terminationGracePeriodSeconds high, add a preStop hook, and pair it with the worker's --drain-timeout: on a deploy the pod stops taking new calls, lets the active ones finish, then terminates — no live call is ever cut. Cloud Run's shutdown is short and not call-aware, so at scale a deploy or scale-in can drop a call mid-sentence. That is the documented "agent goes quiet mid-conversation" failure.

Say it at the whiteboard

"I put the agent on Cloud Run to get it live fast, and it works because LiveKit handles session stickiness at the dispatch layer and I kept the instance warm with no-cpu-throttling and min-instances. For production I'd move it to GKE — not for stickiness, which LiveKit already gives me, but for graceful draining: on GKE a deploy lets live calls finish before the pod dies. Cloud Run can't guarantee that at scale. There's also Cloud Run Worker Pools as a newer middle option — I'd verify its drain behaviour before betting a contact centre on it."
