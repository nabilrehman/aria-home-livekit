Knocking on Your Own Door

Your project has a phone-network address. Here's what happened when we walked up to it and knocked — and what each part of the reply means.

No diagrams pretending to be evidence. Every output on this page came off a real connection to 29ubqywmjjj.sip.livekit.cloud.

01

You have an address on the phone network

This is the part that surprises people. Your LiveKit project isn't only reachable over the web — it has a second front door, one that speaks the telephone network's language, and it has been sitting there open the whole time.

Its address comes from your project ID. Take p_29ubqywmjjj, drop the p_, and that's it:

# your project ID
p_29ubqywmjjj

# your address on the phone network
sip:29ubqywmjjj.sip.livekit.cloud

That one string is the entire carrier integration. When somebody says "integrate Twilio with LiveKit," what they mean is: paste that hostname into a box in Twilio's console. Everything else is bookkeeping.

So the first question is simply whether anything is home.

$ dig +short 29ubqywmjjj.sip.livekit.cloud

161.115.181.100
161.115.180.215

Two addresses, not one — which is the redundancy showing through. And they sit inside the IP ranges LiveKit publishes for exactly this purpose, which is what you'd hand a customer's security team when they ask what to allow through the firewall.

But resolving isn't answering

A name pointing at an address proves nothing. Is anybody actually listening?

02

Somebody is listening

Phone signalling lives on port 5060, the way web traffic lives on 443. So we knocked:

$ nc -z 29ubqywmjjj.sip.livekit.cloud 5060

Connection to 29ubqywmjjj.sip.livekit.cloud port 5060 [tcp/sip] succeeded!

The door opened. Something on the other side is waiting for phone calls.

That still doesn't prove it speaks the language, though. So we said something to it — in SIP.

And this is the good part

There's a SIP message that exists purely to ask "are you there, and what can you do?" It's the same message a carrier sends to health-check a trunk before it trusts you with real calls.

03

We said hello in SIP

The message is called OPTIONS. Here is exactly what we sent — and notice how ordinary it looks. SIP is text, like HTTP, which is a large part of why it's less frightening than its reputation.

──── WE SEND ────
OPTIONS sip:29ubqywmjjj.sip.livekit.cloud SIP/2.0
Via: SIP/2.0/TCP 192.168.1.131:50889;branch=z9hG4bK-a8c7b78d1f33;rport
From: <sip:probe@example.com>;tag=594d82c9
To: <sip:29ubqywmjjj.sip.livekit.cloud>
Call-ID: 2c83b64d144845bc83671074ff7b4265
CSeq: 1 OPTIONS
Max-Forwards: 70
Content-Length: 0

Read it as a letter. From and To are who it's between. Call-ID is the reference number for this conversation. Via is the return address — send your reply back here. Max-Forwards stops it bouncing around forever.

Half a second later:

──── LIVEKIT REPLIES ────
SIP/2.0 200 OK
Via: SIP/2.0/TCP 192.168.1.131:50889;branch=z9hG4bK-a8c7b78d1f33;rport=50889;received=192.168.1.131
From: <sip:probe@example.com>;tag=594d82c9
To: <sip:29ubqywmjjj.sip.livekit.cloud>;tag=a6c61b2e-3a6d-4c07-8a60-15b84139881c
Call-ID: 2c83b64d144845bc83671074ff7b4265
CSeq: 1 OPTIONS
Content-Length: 0

200 OK. The same "200 OK" you know from the web — SIP borrowed HTTP's response codes wholesale. Your project's phone-network door just answered you.

Two details in that reply worth understanding

Look at the highlighted parts, because they're doing real work.

received=192.168.1.131 and rport=50889. We told it our address; it wrote back "and for the record, here's the address I actually saw you arrive from." That's SIP's built-in way of coping with routers that rewrite addresses — the exact same problem STUN solves for WebRTC, handled here inside the protocol itself.

A tag appeared on the To: line. Ours had a tag; theirs didn't, until now. Both sides tagging themselves is how SIP says "this is now a conversation between us two specifically." One tag is a message. Two tags is a dialog.

Why this matters more than it looks

That exchange is not a toy. It is precisely what a Twilio or Telnyx trunk sends before routing production calls to you — same message, same port, same expected reply. Carriers use it to decide whether you're alive.

So you have now performed, by hand, the health check that sits underneath every phone integration you'll ever discuss.

04

The same door, in five countries

Regions stop being abstract the moment you ask DNS about them. The endpoint takes a region name in the middle, and each one is genuinely somewhere else:

You ask forYou get
…sip.livekit.cloud161.115.181.100 · 161.115.180.215global — nearest region
…us.sip.livekit.cloud161.115.180.215same as global ↑
…eu.sip.livekit.cloud161.115.161.165elsewhere
…india.sip.livekit.cloud143.223.91.165elsewhere
…japan.sip.livekit.cloud161.115.166.21elsewhere

Notice the second row. The global name and the US name returned the same address — because the query came from a laptop in Texas, and global routing means "send me to whichever region is closest." That's not a claim in a docs page; that's the load balancer's answer, visible.

Ask from Frankfurt and the global name would have given you the European address instead.

One trap worth carrying

The region code sa means South America for realtime connections and Saudi Arabia for SIP. Same two letters, different continents, in the same product.

Say it out loud

"Integrating a carrier is mostly one hostname. Your project gets a SIP address derived from the project ID, and the carrier's job is to point its origination URI at it. I pinged mine with a SIP OPTIONS and it answered 200 OK — which is the same health check the carrier itself runs before it trusts you with calls. On your side you declare a trunk saying which numbers and which credentials you'll accept, and a dispatch rule saying which room and which agent the call lands in. That's the whole integration."

—

Four things to carry

  1. Your project ID is your phone address. Strip the p_ and add .sip.livekit.cloud. That string is the integration.
  2. SIP is text and it borrowed HTTP's status codes. A 200 OK means the same thing it always did.
  3. OPTIONS is the knock. Carriers use it to check you're alive; you can use it to check the same thing, by hand, in ten seconds.
  4. Regions are real addresses, not settings. Pinning one is a compliance decision that costs you automatic failover.
