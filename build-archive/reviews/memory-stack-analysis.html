Ember Memory Stack Review

The Supabase → Google Cloud PRD, checked against docs current to 28 Aug 2026 and against what Ember already runs. Bottom line first, evidence after.

Verdict: don't move memory into AlloyDB. The PRD's own decision matrix says "Memory Bank for relationship facts, a Postgres table for hard state." Ember already does exactly that split — hard state in Cloud SQL + Firestore, facts in Vertex AI Memory Bank, both preloaded in parallel with the WebRTC handshake. AlloyDB adds ScaNN and Preview AI operators; none of that is on our hot path, and the smallest cluster is ~$110–225/month for a demo that runs on a $50 Cloud SQL instance today.

What's actually missing is small: a forget tool, a metrics line proving Memory Bank retrieval latency (Google publishes none), and hybrid keyword search — which only matters if we ever need exact SKU/part-number matches, and RAG Engine can't do it on its managed store anyway.

Where the PRD is wrong or out of date

PRD claimCurrent docs say
"Cloud SQL supports ScaNN"false alloydb_scann is AlloyDB-only; Cloud SQL has pgvector 0.8.5 HNSW/IVFFlat. Its "Vector Assist" preview is currently disabled.
"ScaNN is 4x faster than HNSW"Up to 4x at ~1M vectors (Google's GloVe-100 benchmark), 10x only when HNSW spills RAM at 1B. Our memory table would hold a few hundred rows — irrelevant.
"Native hybrid search in AlloyDB"Documented pattern is the same manual RRF CTE as Supabase. ai.hybrid_search(), ai.if/ai.rank, BM25 (pg_textsearch, PG17+) are all Preview behind flags.
"Memory Bank adds 150–350 ms sequential overhead"No retrieval latency is published anywhere. Also moot for Ember: retrieval runs in the preload gather, and the greeting doesn't wait for it.
"RAG Engine hybrid search via Vector Search backend"false Hybrid is only available with a Weaviate backend. RagManagedDb and Vector Search 1.0/2.0 are vector-only inside RAG Engine.
"Vertex AI Memory Bank / RAG Engine" namingRebranded at Next '26 (Apr 2026): Gemini Enterprise Agent Platform; Agent Engine → Agent Runtime; Vector Search 2.0 → Agent Retrieval; Vertex AI Search → Agent Search. Say "Agent Engine Memory Bank (Gemini Enterprise Agent Platform)" on the slide.

The three ways to hold memory on Google Cloud

A · Memory Bank (current)

~$0 at demo scale · retrieval unmeasured, hidden by gather

  • Facts extracted and consolidated by Gemini — nobody writes remember() for every preference.
  • Scope = account number is the isolation boundary.
  • Keep. Add forget, pin embedding model, log retrieval ms.

B · AlloyDB EAV + pgvector

$110–225/mo minimum (free 30-day trial cluster) · <15 ms

  • Right when memory is hard state the agent writes deterministically (setpoints, PINs).
  • Loses implicit extraction; contradictions only resolved on exact key.
  • Everything it offers except ScaNN also runs on our Cloud SQL.

C · Add tsvector to Cloud SQL

$0 extra · one migration

  • Only if the panel probes "what about model numbers / error codes?"
  • RAG Engine can't do hybrid on its managed store; Postgres FTS can, next to the data we already own.

What I'd change before the panel

  • Add forget(account, fact) — closes the CRUD story ("remember, recall, forget") the PRD's five-tool set implies. Memory Bank supports delete; ~15 lines in server.py + data.py.
  • Log Memory Bank and RAG retrieval time per call in turn_latency.py — turns "Google publishes no figure" into "we measured 90 ms, and it's off the greeting path anyway."
  • Pin similarity_search_config.embedding_model = gemini-embedding-001 on the memory bank — the default retires April 2027.
  • Slide wording: "Agent Engine Memory Bank on Gemini Enterprise Agent Platform" and cite the 1 Sep 2026 pricing. Say "we chose managed memory over pgvector because facts are extracted, not declared" — that is the one-sentence answer to "why not AlloyDB?"
  • Don't build AlloyDB, anonymous auth, or device control for this demo. If asked: "AlloyDB is a drop-in for our Cloud SQL — same parameterized views, same Toolbox — and we'd move when ScaNN filtered search matters, i.e. millions of vectors, not hundreds."
