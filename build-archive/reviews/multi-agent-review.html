Ember Multi-Agent Review

What production voice-support teams actually do with multiple agents — LiveKit, OpenAI, Google, Parloa, Sierra, Decagon — and what that means for Ember. Sources checked 30 Aug 2026.

Revised recommendation. Yesterday I suggested splitting Ember into a front-door agent plus two persona specialists. The evidence says do something narrower: keep one Ember, add tasks, not personas. LiveKit's own two richest examples (hotel receptionist, healthcare) are one Agent with AgentTasks for bounded jobs — they do not hand off between persona agents. Parloa's production data (24% faster resolution) comes from agents that own one user goal each with deterministic gating, not from "billing bot" vs "tech bot". And every source lists the same #1 failure: context loss and repeat-yourself at the handoff boundary.

For Ember that means: one voice, one identity path, and three bounded tasks — Return/Refund intake, Device troubleshooting, Specialist handoff — plus the out-of-band workers we already run (brief writer, memory extraction, call logging). This is smaller than the three-persona split, cheaper to test before the panel, and it is the architecture LiveKit's docs literally tell you to start from.

Why persona specialists are the wrong split for Ember

  • Ember's questions cross domains in one breath. "My thermostat order arrived broken" is an order and a device. A persona split forces a routing decision the customer never asked for; a task split doesn't — Ember stays, and pulls in Return intake when that becomes the goal.
  • The handoff boundary is where identity and preload get lost. Every source names repeat-yourself as the top complaint. With tasks, known_account, the preload text and memories never leave the agent.
  • 14 tools is under the threshold. LiveKit's tool guidance is 5–12 per turn; Parloa's split signal is "more than two or three scenarios" in one resolution instruction. We're at the edge, and tasks fix it by hiding a task's tools until the task runs.
  • No routing LLM call. Parloa's number comes from routing being free. LiveKit's persona handoff costs a full LLM decision plus a filler line; a task invocation is the same tool call the agent was making anyway.

What stays exactly as it is

  • Ember's greeting, preload, memory tools and simple lookups ("is my thermostat on", "my last order") — a task for a one-shot question is over-splitting.
  • Specialist Desk / WarmTransferTask — already the escalation leg; ReturnIntakeTask returns next: refund_desk and Ember calls it, so the brief is written with the task's typed result in hand.
  • All out-of-band workers.

Cost and risk before the panel

  • Code: three AgentTask classes plus moving eight tool definitions onto them; Ember's prompt shrinks by roughly a third. ~1 day including tests.
  • Tests: the 16 live beats don't change from the customer's side; add one offline test per task (LiveKit's examples ship test_agent.py for exactly this).
  • Demo script: unchanged. The panel sees it only on the architecture slide and in the answer to "how does this scale to 40 intents?" — "we add a task, not forty tools, and the caller never gets transferred between bots."

If Mike asks "why not a triage agent like the LiveKit blog?"

"Their own docs say skip triage when there's one specialist — and their own hotel and healthcare examples don't use one either. Triage earns its keep when departments have different tools, different compliance rules, and different people maintaining the prompts. Aria Home support is one department. What we borrowed from the multi-agent playbook is the part with production numbers behind it: bounded goals, deterministic gating on identity, and never copying context across a boundary."
