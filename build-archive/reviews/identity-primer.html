Ember Identity Primer

How Ember knows who is talking, what each token carries, and why no personal data ever rides inside one.

A customer proves who they are to Google. Our server checks that proof, looks the person up in our database, and hands the browser a 15-minute LiveKit entry pass that carries two things only: a random-looking user ID and an account number. Ember reads the number off the pass when the call connects and fetches everything else from the database herself. If a pass leaked, an attacker would learn "someone with account AH-7104 was allowed into room web-3f9a1c2e for 15 minutes" — and nothing else.

Three passes, three jobs

PassIssued byProvesLivesPersonal data inside?
Google ID tokenGoogle (Firebase Auth)"This browser is signed in as this Google user"~1 h; browser → our server once, over HTTPSyes name, email, picture — never forwarded or stored
LiveKit access tokenOur server (/token)"This browser may join room X as participant Y with attribute Z"15 min, one random roomno opaque uid + account number
Specialist tokenOur server (desk accept)"Specialist Ahmad may join room X"minutes, one roomno identity specialist-ahmad

The Google token is the strong proof; the LiveKit token is a narrow permission derived from it. Strong proofs stay server-side; narrow permissions go to the browser.

The flow, signed-in customer

1–2 · Google says who you are

After "Sign in with Google" the browser holds a Google ID token — a JWT signed by Google. Decoded, shortened:

{
  "iss": "https://securetoken.google.com/bq-demos-469816",
  "aud": "bq-demos-469816",
  "sub": "Kx7pQ2mZ9RaBcD3eFgHiJkLmNoP1",   ← Firebase uid: random, stable, meaningless alone
  "email": "nabilrehman8@gmail.com",
  "email_verified": true,
  "name": "Nabil Rehman",
  "auth_time": 1788111200, "iat": 1788111200, "exp": 1788114800
}

This one has real PII. That is fine because it goes to exactly one place — our server — over HTTPS, and our server neither stores nor forwards it.

3–4 · Our server verifies it without trusting the browser

fb_auth.verify_id_token() checks the signature against Google's published public keys, that aud is our project, that it hasn't expired, and that the user isn't disabled. Any failure → 401 Sign in to start a call. The browser can't forge this; it doesn't hold Google's private key.

5 · Map Google's identity to our customer

Verified email → SELECT … FROM customers WHERE email = $1 → Nabil, AH-7104. The only moment Google's identity and ours meet, and it happens in server memory. (Production note: store the Firebase uid on the customer row at first sign-in and key on that — emails change, uids don't.)

Signed with our LiveKit API secret (_mint() in main.py). Real shape — this example was signed with a throwaway secret; the real one lives only in LiveKit Cloud and Secret Manager:

Deliberately absent: email, phone, address, orders, devices, plan, the Google token, any database ID. Why the uid and not the email as identity: LiveKit writes participant identities and room names into its own logs and dashboards, which are not PII-redacted. An opaque uid in a log is harmless; an email is an incident.

7 · The browser joins; LiveKit checks the signature

Change AH-7104 to AH-4821 in the payload and the HMAC signature breaks — the join is refused. The browser never had the secret. LiveKit creates the room and dispatches anycompany-agent.

8 · Ember reads the attribute — she never asks the browser

participant = await ctx.wait_for_participant()
known_account = participant.attributes.get("aria_account", "")

Attributes set from the token are server-verified; the client can't overwrite aria_account from JavaScript because we didn't grant canUpdateOwnMetadata. Ember then calls /api/preload?account=AH-7104 with a service API key the browser never sees, and greets by name. The personal data went database → agent process — never through the browser or the token.

Guest path (the phone-call experience)

POST /token/guest mints the same token with identity guest-1a2b3c4d, name "Caller", and no aria_account. Ember sees no account, asks for a phone or account number, and calls the Toolbox lookup. When it succeeds, the agent code — not the model — captures the returned account into known_account. From then on every scoped tool uses that value.

The model never asserts an account; it can only ask the database, and only the database's answer becomes the account. Honest limitation: on this path, knowing the account number is the credential — exactly like real phone support, which is why real IVRs add a PIN or last-4. The signed-in path is the strong one.

Where the account number goes next — the isolation chain

token attribute ──► known_account (agent) ──► X-Account header ──► /api/my/orders
                                                                        │
                                          parameterized secure view: WHERE account = $@account
                                          role aria_app: SELECT on views only — NO base tables
  • Agent → server: X-Account: AH-7104 plus the service API key; no key, no answer.
  • Server → database: connects as aria_app, which has no grant on orders, devices, customers — only on views that take the account as a parameter. The filter is part of the view, not the query, so no query as aria_app can return another account's rows.
  • Memory Bank: scope {"user_id": "AH-7104"}; a different scope returns nothing.
  • Firestore call history: keyed and filtered by the same account.

Even if the LLM were tricked into asking for Sarah's order, the database returns empty. The prompt is not the security boundary; the database is.

Specialist tokens (transfer)

When a specialist clicks Accept, the server checks the desk PIN and mints a token for identity specialist-ahmad, room = the customer's room, TTL minutes. The brief (already masked: AH-••04, [phone]) is served by the API, not embedded in the token. Ember sees a specialist-* participant and steps back.

What a Google-literate panel will ask

Why Firebase and not Identity Platform?
Same engine. Identity Platform is Firebase Auth with enterprise features (SAML/OIDC, multi-tenancy, SLA). The swap is configuration, not code.
Why not room metadata / dispatch metadata like the workshop video?
Participant attributes are per-person and signed into the token. Room metadata is shared by everyone in the room and editable by anyone with the grant. For "who is this caller", attributes are the right primitive.
Isn't the account number on the token PII?
It's a customer identifier, not personal data, and it's the smallest value that lets the agent skip a round trip on the greeting path. Looking it up from the uid instead would cost one more call for no security gain — the uid is just as sensitive as a lookup key.
How would phone (SIP) callers get identity?
From the trunk: LiveKit sets sip.phoneNumber as a participant attribute. We read it exactly like aria_account and call lookup_account_by_phone before she speaks — same code path as the guest flow, minus the asking.
Where are the secrets?
LiveKit API secret: LiveKit Cloud agent secrets and Cloud Run env from Secret Manager. Firebase: none — verification uses Google's public keys. DB passwords and the service API key: Secret Manager, bound to the aug24-agent@ service account.
